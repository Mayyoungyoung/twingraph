# value-v7 基准审计（实现前冻结）

审计日期：2026-09-18  
代码分支：`research/value-v7-fulltask-view-ablation`  
审计基线：当前工作树 `55707a4`（父分支为 `research/value-v6-robust-vision`）。

## 结论摘要

当前 v6 的任务范围仍是
`assemble_five_parts_from_supplies_and_release_no_stroke_test`。它是五个零件的装配与释放任务，**没有把擦拭、清洁验收或最终滑动功能测试接入价值标签和物理执行**。仓库中虽然存在 `simbench/assembly/wiping.py`、`library.py` 的擦拭技能，以及 `assembly/task.py` 的行程测试，但它们没有被 v6 的候选采集器和 v6 物理 runner 作为同一个完整任务执行。

因此，v6 的离线结果可以作为视觉消融的历史基线，不能被解释为完整清洁—装配—功能测试系统的结果，也不能把现有视频称为完整任务视频。

## A. 旧 v6 结果复核

旧报告和 `evaluation.json` 的 16 个 held-out 场景、192 个候选的结果如下（Top-4 命中指候选池内是否包含经验鲁棒成功候选；不是新 target 上执行成功率）：

| 视角 | Accuracy | Balanced Accuracy | ROC-AUC | Brier | Top-4 命中 | Top-4 平均经验成功率 | 全池平均经验成功率 | 随机 Top-4 命中期望 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| none | 0.640625 | 0.640143 | 0.690838 | 0.195955 | 0.875000 | 0.640625 | 0.489583 | 0.861742 |
| task | 0.666667 | 0.667390 | 0.713309 | 0.193159 | 0.875000 | 0.661458 | 0.489583 | 0.861742 |
| top | 0.671875 | 0.673144 | 0.713634 | 0.197201 | 0.875000 | 0.661458 | 0.489583 | 0.861742 |
| both | 0.645833 | 0.648285 | 0.704842 | 0.189400 | 0.750000 | 0.588542 | 0.489583 | 0.861742 |

v6 按验证集 Brier 选择的模型为 `both_43`（验证 Brier 0.117183），冻结阈值约 0.720660。旧系统批次中，Top-4 + twin 的独立 target 成功为 25/36（0.694444），Full-12 + twin 为 27/36（0.750000）；两者均有 2/12 场景 abstain。Top-4 平均决策耗时约 674.5 s、总耗时约 835.9 s；Full-12 平均决策耗时约 1679.0 s、总耗时约 1819.3 s。这里的 36 次是独立 target 执行次数，不能与离线经验候选命中率混写。

随机基线在每个场景有 `N` 个候选、其中 `m` 个经验鲁棒成功候选、无放回抽 `K` 个时按

`P(hit) = 1 - C(N-m, K) / C(N, K)`

计算；当 `m=0` 时为 0，当 `N-m < K` 且 `m>0` 时为 1，组合数边界按 0 处理。这个量是“经验成功候选集合的命中率期望”，不是“被选计划在新的 target 扰动下的成功率”。后者必须通过独立 target 物理执行估计。

## B. 真实任务范围与调用链

1. `simbench/value/stage_v6.py` 的 `TASK_SCOPE` 由 `stage_v5.py` 提供，并且 `build_pool`、`rebind_plan` 直接复用 v5 装配候选生成器。
2. `stage_v5.stage_calls()` 只生成检测、抓取、搬运、对准、按压、放置、释放和装配验收调用；没有 `wipe_surface`、清洁验收，也没有把手安装后的双向滑动验收。
3. `simbench/assembly/task.py` 存在一个独立装配演示，其中的 stroke 在把手安装前执行，不能代表“完整产品安装后功能测试”。
4. `simbench/assembly/full_demos.py` 可以调用擦拭再装配，但它仍然没有可恢复的污迹环境状态、阶段化成功标签，也没有把最终测试接到 v6 价值标签和 runner。

## C. 观测、twin 与 target 边界问题

- `library.Session.observe_parts()` 从 `ctx.obj_pos()` 直接构造观测；`estimate_pose()` 对四元数直接读取 `ctx.obj_pose(part)[1]`。这意味着位置虽有少量模拟噪声，姿态仍是隐藏真值，且接口名称容易把仿真真值误称为 detector 输出。
- `stage_v5.grasp_catalogue()`、初始路径和部分几何检查直接从 `session.ctx` 读取零件位置；候选生成没有统一冻结的观测对象。
- v6 的 `observed()` 另外读取 `stage_v5.observed()` 后再附加 RGB-D，但结构化决策字段仍来自 simulator truth，未明确区分隐藏环境状态、机器人观测和 twin 估计。
- `physical_v6.RobustPhysicalRunner` 对 target 主要加入位置感知/物理扰动，没有统一的姿态观测误差和 manifest；不能证明 twin 与 target 使用了相互独立的随机命名空间。

## D. 候选差异审计

当前候选对象中确实存在候选顺序、抓取 yaw/高度、间隙、速度/力参数和搬运路径字段，但必须逐项确认这些字段是否进入 `stage_calls()` 的真实控制调用。候选 ID、计划哈希和摘要属于元数据，不能作为模型输入或执行差异。v7 将增加语义去重和执行参数审计：若两个候选展开后的有效控制调用完全相同，只保留一个语义实例并在报告中计数。

## E. 真实代码问题与 v7 修改边界

### 必须修正

1. 建立统一 `Observation/SensorBackend`，在一次决策边界冻结结构化观测；位置和偏航同时加噪，记录 seed、噪声参数和 backend 名称，明确这是“模拟传感器代理”，不是已完成的真实 RGB-D 位姿检测。
2. 候选生成和 twin 几何检查只能读取冻结观测；target 执行重新绑定到独立真实初始状态和独立扰动，不能复用 twin 最终状态。
3. 增加可见污迹、接触条件驱动的清洁状态和 `cleaning_pass`。悬空经过、静止按压、只碰侧壁和漏擦必须失败，真实工作面接触且有切向运动才可减少污迹。
4. 将五零件装配、工具归还、把手安装后的双向滑动测试和最终回收接成同一任务，保存 `cleaning_pass`、`assembly_pass`、`functional_test_pass`、`final_release_and_retraction_pass` 及失败原因。
5. 扩大并分级随机化（L0/L1 训练、L2 留出测试），同时记录拒绝率和参数 manifest；不修改旧 v6 数据和标签。
6. 固定 12 候选池，加入随机 Top-4、几何启发式、Value-Top1、Value-Top4 + twin、Full-12 + twin 等同预算对照；报告全场景成功率、接受后成功率、abstain 率、执行次数和失败分类。

### 不在本次偷偷改变的部分

- 不改写旧 v6 的 `simbench/value` 数据、模型和报告。
- 不把仿真真值经过传感器模型包装成真实视觉检测网络；报告中会显式标注模拟感知代理。
- 不修改测试标签、删除困难样本、按结果挑场景或把 target 结果复用于 twin。
- 不自动驱动真实机械臂，本轮只运行仿真、训练和分析。

## F. 基准局限

以上数字来自已保存 v6 结果和源码审计，未重复昂贵的旧物理执行。v7 的新标签、完整任务、L0/L1/L2 随机化、四视角训练和系统对照必须在新分支、新数据目录和冻结 manifest 上重新完成。任何尚未实际运行的表格将明确标记为 pending，不把离线重放冒充在线测量。
